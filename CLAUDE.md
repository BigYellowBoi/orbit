# Orbit – working notes

Training log for Louis (BigYellowBoi): a rotating split (Push 1, Pull, Push 2, Legs; optional Upper/Lower/Push/Pull/Legs), WHOOP and MacroFactor imports, maintenance goal by default, with an optional Overload mode for the Aim (Plan → Targets; `S().goal` 'hold' | 'grow', `progRate`, `growFrom`). Aim logic lives in engine.js; check changes with `node test/engine.mjs` (follow-the-Aim: maintenance must stay flat, overload must climb at each rate; plus rotation, PRs, maintenance badge, bodyweight scoring). For refactors, also run it with `OLD_ENGINE=<path to the previous engine.js>` to prove identical results. Lift lookups go through one cached index (`lix()`, keyed on STATE.v + today), so any code that changes STATE.w must go through `changed()`/`bump()`. The Strength tab's 4 wk badge compares medians of each session's best set (v1.17), not single bests. Bodyweight lifts score by reps unless the exercise has `bwf` (share of body weight, set as "Body weight counted %" in the exercise editor), then e1RM on share × trend weight at the set's date + added kg; the ab roller has none. Single-file vanilla JS app, dark theme, Geist fonts. No framework, no bundler.

User preferences: short answers, never use em dashes (in replies or UI copy). Keep the soft neon-purple glow on the header logo (he likes it). iOS draws a blurred band over the top of home-screen apps reaching ~14pt below the status bar; the header row sits 14pt lower in standalone mode (`--hdrdrop`), the only position he found sharp (v1.3 and v1.5 tests, tinted headers didn't help).

## Sync helper (worker/)
`worker/orbit-sync.js` is a Cloudflare Worker (free plan) Louis runs himself: WHOOP API v2 (OAuth, webhooks, cron every 10 min, history backfill) and Apple Health numbers from an iPhone Shortcut (`POST /health`), both written into `orbit/dy/YYYY-MM.json` in `orbit-data` via the GitHub contents API. Pages app only; the artifact isn't touched. Setup is in `worker/README.md`; secrets live in Cloudflare only. Free plan: 50 outside requests per run (worker budgets 45), so keep request counts in mind. Since v1.24 a verified WHOOP webhook syncs straight away (`ctx.waitUntil(run({ force, hook }))`; the `dirty` flag lets the next cron retry if it fails). Cron is `*/5` (Louis must set it in Cloudflare): every run polls today's cycle (`pollToday`, 1 WHOOP call; GitHub and the KV status write only on a change or every 25 min), full sync at fixed local times every 3 h (`fullSlot`: hh:00–04 for hh % 3 == 0, once per slot via `st.fullSlot`; caught up once if a slot was missed). Scheduled runs stamp `lastSync`/`todayAt` with `ev.scheduledTime`, so the Data card shows round 5-minute times (Louis found 8:11pm unsatisfying); notification syncs record `hookAt` and leave those alone. Tests pass `scheduledTime` explicitly (`offSlot()`), so they don't depend on the clock. v1.29 traffic: helper meters every outside request (`mfetch`: per service n/ms/bytes, GitHub rate headers), keeps today's usage in `st.use` (WHOOP calls, GitHub, KV writes, runs, notifications), a 25-entry sync log (`logEv`; v1.33: a newer entry replaces one it supersedes: same kind, notifications per thing, a full check also drops earlier steps polls; history steps stand; gh.js collapses the same way for older logs) and `dataAt`/`dataWhat` (when data actually arrived, notifications included). Status is now written on every run so counts are exact (~290 KV writes/day of 1,000). Apple Health posts keep their own `hlog` key (log, counts, latest), replacing `healthAt` (still read as a fallback). status.json v2 adds usage, net, log. The app meters its own GitHub and helper requests (`NET`, `netNote` in gh.js); Data shows a Latest data row and a live Traffic card (`Helper.traffic`, refreshed in place every 2 s, helper status every 15 s while the Data screen is open). Upload speed isn't measurable from fetch, so only download speed (≥2 KB) is shown. Token renewal: scheduled runs renew 15 min before expiry and hook runs only within 60 s, so two runs never spend the single-use refresh token together. Budget ~600 WHOOP calls/day of 10,000, ≤45 per run, KV writes well under 1,000/day. Test with `node test/worker.mjs`. Louis pastes the code into Cloudflare by hand, so tell him when `orbit-sync.js` changes.
Health history: `tools/health-to-orbit.py export.zip` (stdlib, streams the XML) makes the Orbit Health .json that Data → Apple Health imports; same fields and rounding as `/health` (iPhone-only steps, kJ → kcal, last weight of the day, headphone energy average). Louis attaches export.zip to the chat and gets the .json back; never commit either. He uses Health Auto Export (paid app, REST API automation) instead of the Shortcut: `/health` also accepts its JSON (`data.metrics[]`, `fromHae()`; Summarize Data on, Time Grouping Day; key as `?key=` or an `x-sync-key` header; an empty run returns 200 without a commit). That format has no headphone minutes, so `hpm` only comes from full exports. His export held every MacroFactor nutrition sample twice while Health itself shows single totals, so the converter dedupes exact duplicates.
The Data screen's **Automatic sync** card (Pages only, `Helper` in gh.js) reads `<helper>/status.json` (CORS *, no secrets: WHOOP connected/checkedAt/error/history, Apple Health last POST from KV `healthAt`); the address is `S().helper`, entered once on that card.
Day fields from it: WHOOP keys as the CSV import plus `stp` (WHOOP steps); Health: `stpi` (iPhone steps), `hp` (headphone dB, time-weighted energy average), `hpm` (headphone minutes), `kcal/p/c/f/wt`. Orbit derives trend weight and expenditure (`derived()` → `xpRun()` in engine.js, v1.32) where MacroFactor's export has none: trend = MacroFactor's own method (weigh-ins linearly interpolated, then 10%/day average; matches its export exactly); expenditure = 2-state Kalman filter [weight, expenditure] observed through that trend, Hall/Forbes energy density (fat mass from `XP.bf` 16%), MF's missing-data rules as read off its export (v1.35): the update into day d pauses when >3 of days d-6..d-2 lack usable intake (matched all 28 real pause days); blank or partly logged intake is estimated as the mean of usable days in the 7 before. MF counts a low day as complete unless you confirm its partial-logging prompt; Orbit asks the same on Body (`partialCard`, flags under 70% of the 6 days before via `partialFlags`, answers in synced `S().partial[date]`, true = partly), and an unanswered day under half counts as partly logged. MF's tw/exp win and reseed the state. Against his MF export (Feb to Oct 2026): 19 kcal/day with his MF partial answers (fitted from the export; held-out halves 18 to 22), 33 unanswered (v1.32: 31, old method 252). Fitting more parameters overfits (held-out 34 to 55), so only the intake-estimate weighting was fitted on top of v1.32's values. Steps were tried (nudge and faster updates) and didn't help, so they're out. Retune by running the filter on intake + scale weight only and scoring against MF's Expenditure sheet; never commit the export. The GitHub merge combines day fields from the repo and a dirty local day (local wins per field).
